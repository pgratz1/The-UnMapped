## What was checked

The draw is made only after `q == p.ruling` has been ruled out (`:551-553`), so only on a change of people (5.1). `pick(u, span + 1)` with span in [0, 1000] is within `pick`'s [1, 2^32]. A settlement taken twice by the same realm in different years draws with different years; in the same step it cannot change hands twice in the ledger.

## Advisories

**A1. `word_since` is kept when a race has no alive realm** (`relations.cpp:1343-1345`). Spec 4.2 resets `word_since` to 0 "if h > `meet_sealed_hops` (or no key)". When one race of the pair has no alive visible civilization (every realm ended; `visible` only excludes realms founded in this step), the code `continue`s before computing a key, so `word_since` keeps its year and the 300 (shipped 150) years run on while that people has no realm, and a realm it founds later can meet by word at once. Deterministic on every platform, but it changes which worlds meet by word against the spec's text. Fix: set `pairs_[i].word_since = 0` before that `continue`, or restate 4.2 to count only steps with a key. Related, weaker: 0 is both "not set" and a year, so a pair that first comes into reach in a step of year 0 would be set again at the next step (only if both peoples can have a realm at year 0).

**A2. A common-enemy entry keeps the event of the last relation by key** (`relations.cpp:1046-1047`). When realm z is at war with two realms of race r at once, `civ_foes_[{z, r}]` ends with the opening event of the relation that comes last in `RelationKey` order, not necessarily the later war. Deterministic; it decides which `war_declared` a warmer turn cites. Fix if the spec means the latest: keep the larger event when the year is the same.

**A3. "The last 8" contributions are by insertion, not by event id** (`relations.cpp:999-1003`). `war_foes` runs after `read_log` and credits with the opening event of a war, which can be older than events credited earlier in the step, so the list is not ascending and the dropped entry is not always the smallest id. Deterministic (fixed call order) and sorted before use by `causes_of`. Note for P5-04's callers of `credit`.

**A4. `credit()` is public** (`relations.hpp:123`). Safe now. A later caller must call it at a fixed point of a step (inside a subsystem's `run`, not from code whose order depends on how many subsystems ran or on a container of pointers), and its event argument must be an existing event id; P5-04's spec should say so.

## Not extended

Candidates considered for the lint and rejected: a reference returned by a caching accessor into a member vector of vectors (`border_hops`, `within_contact`) is safe here because the outer vector is sized once; a rule would need data flow and would flag every such cache. A variable shift `1 << x` is guarded by an explicit bound and is too common for a text rule.
