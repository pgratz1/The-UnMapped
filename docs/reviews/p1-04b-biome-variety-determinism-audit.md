Auditor: determinism auditor, 2026-11-18. Change audited: `git diff main...p1/04b-biome-variety`, merge-base `eb0445e` ("Proposals: schema 4 (per-world temperature offset)"), branch tip `b19c4d9`. Line numbers are those of `b19c4d9`.

Scope: `worldgen/src/stages/biomes.cpp` and `worldgen/include/worldgen/stages/biomes.hpp` (B2b, B2c, B4's two comparisons, the seams); `worldgen/src/stages/climate.cpp` and `stages/climate.hpp` (C2b, C3 with the offset, the climate row); `core/streams.hpp`; `version.hpp`; `worldgen/src/data/kinds.cpp` (two rule fields, six tuning fields, `temp_offset_max_c`); `db/schema.hpp`, `db/writer.hpp`, `worldgen/src/db/writer.cpp` (schema 4, three-column insert); `worldgen/src/inspect/geography.cpp`, `report.cpp` and `inspect/geography.hpp` (`temp_offset_c`, the climate-table reasons); the twelve biome files and `worldgen/biomes.toml`, `worldgen/climate.toml` in `game/data/` and both fixture roots. Test files were read only where they define data or golden values.

**Verdict: pass.** No blocker, no should-fix. On every input `generate` can produce, the `temperature` layer, the `climate` row, the `biome` layer and the `biome` table are functions of the seed, N, the stored input layers and the loaded data, independent of compiler, thread count, row-block partition, data-file order and directory-entry order. Every new arithmetic step is exact integer or fixed-point work, and every bound claimed in the code or the spec was checked against the types actually used, by reading and by running at the extremes. Seven notes (section 1), one of them a wrong bound in the amended spec text (N6) and one the P1 golden files that still hold 0.8.0 values (N7). No lint rule added (section 5).

Classification: **blocker** can change output between platforms, compilers, standard libraries or thread counts; **should-fix** is fragile or breaks a stated contract and needs action before merge or soon after; **note** is for the record.

### Notes

**N1. B2b (river distance) is exact, and the `int32` internals with 2^30 for "no target" overflow nowhere.** `biomes.cpp:259-310` (`FAR32`, `relax`, `river_distance_cells`), `:564-577` (seam), `:704-716` (stage), `:166-168` (`d34_max`), `:182-189`.
- Scan orders: the forward pass visits y = 0..H−1, x = 0..W−1 with candidates (x−1, y) +3, (x−1, y−1) +4, (x, y−1) +3, (x+1, y−1) +4; the backward pass visits y = H−1..0, x = W−1..0 with the mirrored four. Both work in place and skip neighbours outside the grid, exactly as B2b states.
- Overflow: every grid reaching the passes has passed `geo::check_grid` (≤ 2^24 cells): the stage calls it at `:680`, and the seam calls it through `check_grid_array`. Finite values are < 4 × max(W, H) ≤ 2^26, which also covers a 1 × 2^24 strip. A candidate is at most `FAR32 + 4` = 2^30 + 4 < 2^31, and `relax` stores it only when it is smaller than the current value, so `FAR32 + 3` is never stored and a FAR cell stays exactly `FAR32`. The two static asserts (`:266-267`) state both facts: 16 × 2^30 > 3 × 32766, and 4 × 2^24 + 4 < 2^30. The seam maps `FAR32` back to `BIOME_D34_FAR` = 2^40. No finite value can equal 2^30, so the mapping is exact.
- Same comparisons as with 2^40: `d34_max` is `INT64_MAX` for the sentinel 32767 (both FAR values pass) and otherwise ≤ (3 × 32766) div 16 = 6143 (both FAR values fail).
- `d34 ≤ (3 × bound) div 16` ⟺ `16 × d34 ≤ 3 × bound` for d34 ≥ 0 and bound ≥ 0 (floor of a non-negative quotient, d34 an integer). The seam was run for every bound 0..32767 with d34 at the threshold, ±1, +2, 0, 2^30 and 2^40, and the arithmetic identity for every d34 in 0..6200: no difference (section 4).
- The seam result equals the closed form min over targets of 3 max(|dx|, |dy|) + min(|dx|, |dy|), and 2^40 everywhere without a target. This holds on 6,000 random fixtures, a quarter with no target and a quarter all target, including 1 × N and N × 1 strips, on GCC, Clang and ASan/UBSan. The 2048² grid with no river is all 2^40. One corner target gives 8188 at the far corner. A 1 × 2^24 and a 2^24 × 1 strip give 50331645 = 3 × (2^24 − 1) at the far end under UBSan, with no report.
- B2b is sequential (no thread involvement) and uses no stream.

**N2. B2c (wet share) is exact for any block partition and any thread count, and every intermediate fits the type that holds it.** `biomes.cpp:331-447` (guard, axis totals, `box_rows`, `box_columns`, `wet_count_cells`), `:579-596` (seam), `:717-726` and `:755-758` (stage).
- Exactness of the split. G6 blocks depend only on H (64 rows, `geo/blocks.hpp`). `box_rows` works on whole rows, so each row is independent. In `box_columns`, every block starts its own running column sums from the clipped window of its first row: rows max(0, y_begin − h) to min(H − 1, y_begin + h). It then slides by adding row y + h + 1 and removing row y − h. So each output row is computed from `in` alone, with no state carried between blocks, and the result equals the clipped box for any partition, even blocks of one row. Each of the four passes is a separate `for_each_row_block` call that joins before the next starts. Each pass reads a buffer no block writes (a→b, b→a, a→b, b→a), so "pass 2 starts after pass 1 has finished" holds. Running the x passes before the y passes is exact: the clipped 2D box is the product of two clipped intervals, so it is separable, and the axis operators commute. ThreadSanitizer reports nothing (section 4).
- Types. h = r div 2 ≤ 62, not r. So the largest window is 125 cells per axis, and the count and total reach at most 125^4 = 244,140,625 < 2^28, not (2·125 + 1)^4 ≈ 3.97 × 10^9. That larger value would not fit `int32`, but nothing reaches it. Intermediates: after one x pass ≤ 125; after two ≤ 125² = 15625; after the first y pass ≤ 125³; after the second ≤ 125^4. Each is stored in `int32`, cast from an `int64` running sum (`box_rows` `s`, `box_columns` `s[x]`), which never holds more than one window. `axis_triangle_total` sums `clipped_count` in `int64`, ≤ 15625 per axis. The total `tx[x] × ty[y]` is formed in `int64`, ≤ 125^4. Loop indices `x + h + 1` and `y + h + 1` stay below 2^24 + 63, inside `int32`. Under ASan/UBSan, the 2048² all-wet grid with r = 125 gives count = total = 125^4 on interior cells and count = total everywhere. The 1 × 2^24 and 2^24 × 1 strips with r = 125 give 15625 / 15625 in the middle and are each other's transpose. No report on any of them.
- Reference: the seam's count and total were compared with a separate int64 summed-area table and, on small grids, with direct double sums. Fixtures: 3,000 small (1 to 30 per side, r 0..125 with many small r) and 150 multi-block (H 60 to 400, so up to seven blocks), including strips, all-wet, none-wet and all-ocean. Each was run at threads 1, 2, 3, 5 and 8, on GCC, Clang, ASan and TSan builds. 0 mismatches. `wet` was recomputed independently as `hand << 32 ≤ 10 × wet_hand_m.raw` in `__int128`.
- Entry guard (`:339-353`). The guard runs in the order of P1-04 7 as amended on `main`: (1) r_cells in 0..125; (2) W, H ≥ 1 and W × H ≤ 2^31, computed in `int64`; (3) ≤ 2^24 cells; (4) array lengths. It runs before any allocation. Observed messages: r 126 with an empty grid and no arrays reports r; a 0 × 5 grid reports (2); 65536² reports (2) with no allocation; 4097² and (2^31 − 1) × 1 report (3); a short array reports (4). `threads` is checked after the guard (`:582`); 10.5 does not order it, so this is not a contract issue.
- `wet_window_m` 2001 to 2015 from a hand-built tuning gives r = 125 and passes the guard. Confirmed harmless: on 1024 seed 3, the stage's `biome` layer with 2001, 2008 and 2015 equals the layer with 2000, and 2016 is fatal at the guard (`B2c window r_cells outside 0..125`). The window does matter: 2000 gives a different layer from the shipped 480 on that world. A negative `wet_window_m` maps to r = −1 (`:722`) and is fatal. Very large values give a large r, also fatal, with no overflow (`wet_window_m / 16` on `int64`).
- Skipping. `any_rule_uses_river_distance` and `any_rule_uses_wet_share` (`:312-329`) walk exactly the definitions and rules `compile_lookup` compiles (`land_order`) and test the sentinels B4 skips (32767; raw 0). When a step is skipped, `CellWet` keeps 2^40 / 0 / 1 (`:111-115`), and every compiled rule then has `d34_max` = `INT64_MAX` and `wet_need` = 0, so those comparisons are not evaluated. Neither step touches a stream. Demonstration on 512 seed 0 and 1024 seed 3: set every rule to the sentinels, which skips both steps; then add one never-matching rule (elevation ≥ 3000 m and ≤ 0 m) with `wet_frac_min` 0.5 and `river_dist_max_m` 100, which forces both steps to run. The two `biome` layers are identical. Skipping also skips the `river_dist_class_min` check and the B2c guard, as 10.5 states. A bad rule field is reported before either (observed order: `biomes: rule: coast_max_m outside its schema range` with a bad class and a bad window).

**N3. B4's new comparisons are exact at every threshold.** `biomes.cpp:126-189`, `:617-649`.
- Share: need = `mul(wet_frac_min, ws).raw` (P0-01 `mul`, RHA, checked), computed once per rule per world and then non-negative. Range: wet_frac_min ∈ [0, 1] and ws ∈ [0.25, 4] are both checked first, so need ≤ 2^34. The comparison `need × total ≤ count × 2^32` is evaluated in `U128`: `mul_u64_wide`, and `count` placed as `{count >> 32, count << 32}`, matching the `{hi, lo}` field order of `U128`. Both sides are therefore exact for any `uint64` inputs, not only within the 2^62 bound of P1-04 7. Results:
  - 3,000,000 random rules and cells, with counts concentrated within ±2 of the threshold, plus raw 1, ONE, "0.45", ws 0.25, 1.5 and 4, and totals up to 125^4: identical to an `__int128` evaluation with an independent RHA `mul`.
  - The spec's cases: 0.45 at ws 1 passes at exactly 9/20 and fails at 8/20. At ws 1.5, need is 2899102925, 27/40 (exactly 0.675) fails and 28/40 passes.
  - A need that rounds to 0 is skipped, which is allowed by B4.
- Sentinels: `river_dist_max_m` 32767 → `INT64_MAX`; `wet_frac_min` 0 → need 0, skipped. These widened values are only compared, never used in arithmetic.
- Rule checks (`check_rule_ranges`, `:126-146`): the nine old fields, then `river_dist_max_m` and `wet_frac_min` in declaration order; then the rain scale, then the wet scale (`compile_rule`, `:154-160`). In `biome_lookup`, every rule is checked in B4 order before any cell is evaluated. The cell inputs come first (`checked_cell`, `:620-634`: S2, then d34, then count and total). Observed: a bad `river_dist_max_m` together with a bad wet scale reports the field; d34 −1 together with a bad rule reports d34; count > total and total 0 report the share message. This is the order of 10.5.
- Data: the twelve files in `game/data/biomes/` are identical to both fixture roots (`diff -r`). Every rule, one per land biome with rules, writes both new fields. The loader requires them in any case (`kinds.cpp:228-229`, `Field::required`). In the canonical encoding the two fields follow `coast_max_m` in table order. The six tuning fields follow `drain_river_class_min` (`kinds.cpp:280-285`), and `temp_offset_max_c` is last in `worldgen.climate` (`kinds.cpp:429`), as in P1-03 4. Data roots written in forward and in reverse order, on tmpfs (reverse readdir order) and on ext4 (hashed order), give the same file hashes for 512 seeds 0 and 42 (section 4).

**N4. C2b and C3: one draw from the offset's own stream, never shared; the offset enters C3 as exact fixed point.** `climate.cpp:172-184`, `:187-201`, `:206-224`, `:507-511`, `:547-551`; `streams.hpp:59-61, 100`.
- `climate_temp_offset_dc` builds a fresh `Rng(stream_key(seed, "geo.climate.temp_offset"))` and calls `uniform_i64(−M, M)` once. With M = 0 it builds nothing. No other code uses that key: `geo.climate.wind` and every other `Rng` or noise key is derived independently from the seed and its own name, and `all_stream_names` is read only by a test. So skipping the draw cannot move any other stream. `wind_toward` is unchanged from 0.8.0 on both comparison worlds, and rainfall with `temp_offset_max_c` 0 equals the stored rainfall on five worlds (section 4).
- M = `mul_int(temp_offset_max_c, 10).round_int()`, after a range check of [0, 5] (fatal at −1 raw and 5 + 1 raw, observed). Check method: 14,000 checks for every tenth 0..50 at raw ±3 around each half-tenth, over 40 seeds each. All equal an independent RHA of raw × 10 / 2^32 followed by the reference draw. "0.04" gives 0 and "0.05" gives M = 1, as in P1-03 5.1. Seeds 0 to 11 give 20 10 −11 14 2 8 6 −2 −19 −13 11 10 and seed 42 gives 9, the values of P1-03 5.1. Seeds 0 to 1999 equal `Rng(...).uniform_i64(−20, 20)` called independently. With M = 50, both −50 and 50 occur within 10,000 seeds. `uniform_i64` is the project's integer generator, and its `uint64 → int64` conversion is defined in C++20.
- C3: `off = Fx::from_ratio(offset_dc, 10)` (RHA, symmetric for negative values) and T = ((t_sea + off) − lap) + tn. Every operation is checked `Fx`, and T is evaluated in the spec's order. Both seams are fatal outside −50..50 before any work: ±51 fatal, ±50 accepted (observed). C3 still runs in G6 row blocks and reads only immutable inputs.
- The climate row calls `climate_temp_offset_dc` again (`:550`), the same pure function of the seed and the tuning used for the layers (`:510`). The stored value equals the C3 offset on five worlds (section 4). The writer range-checks −50..50 (`writer.cpp:507-509`) and binds three integer columns into the spec's statement (`:512-515`).

## 5. Lint rules

None added. No finding is a pattern a banned-construct rule could catch. The narrowing casts to `int32` in B2b and B2c are bounded by arguments that depend on the window and grid limits, and a rule against `static_cast<std::int32_t>` would be noise across the codebase. Every other construct in the change is already covered (`unordered`, `std::sort`, directory iteration, floating point, `<random>`, flags).
