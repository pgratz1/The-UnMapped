Test files were read only where they define data (fixtures, golden file).

**Verdict: pass.** No blocker. On every input `generate` can produce, the `biome` layer and the `biome` and `climate` tables are a function of the seed, N, the stored input layers and the loaded data, independent of compiler, thread count, row-block partition, data-file order and directory-entry order, and every arithmetic step on that path is exact integer or fixed-point work with a stated bound. One should-fix (S1: an unchecked `int64` multiply in `compile_rule` reachable only through the public seams with a hand-built rule). Eight notes, one of them (N8) the stale P1 golden file the validation specialist re-records. No lint rule added (section 5).

Classification: **blocker** can change output between platforms, compilers, standard libraries or thread counts; **should-fix** is fragile or breaks a stated contract and needs action before merge or soon after; **note** is for the record.

## 1. Findings

### Blockers

### Should-fix

**S1. `compile_rule` multiplies the elevation bounds by 10 in plain `int64`; a hand-built `BiomeRule` passed to the public seams overflows (undefined behaviour, not a fatal error).** `biomes.cpp:114-115` (`10 * r.elev_min_m`, `10 * r.elev_max_m`), reached from `biome_rule_matches` (`:315-321`), `biome_lookup` (`:323-329`) and `compile_lookup` (`:140-153`, used by `biome_layer`).

`BiomeRule`'s fields are plain `int64` (`biomes.hpp:67-77`); only the loader's schema bounds them (`elev_*_m` int(0, 3000), `kinds.cpp` `biome_rule_schema`). `biome_definitions_from(span)` re-checks codes, water bodies, fallback and priorities for hand-built input (`biomes.hpp:111-116`) but not the rule fields, and the two lookup seams take a `BiomeRule` or `BiomeDefinitions` directly. Observed with the `linux-clang-asan` library: `biome_rule_matches` with `elev_min_m = 2^61` reports `biomes.cpp:114:51: runtime error: signed integer overflow: 10 * 2305843009213693952 cannot be represented in type 'std::int64_t'`. In a release build the wrapped bound is compiler-dependent in principle (the optimiser may assume no overflow), so two compilers could disagree on such a call. The other compiled bounds are safe: `mul_int` (rain, hand) and `slope_s2_limit` are checked and fatal, and the sentinel widening (`:106-121`) feeds comparisons only (`compiled_matches`, `:123-128`), never arithmetic.

**No world is affected**: `run_biomes` builds every rule from a validated record, where `|10 × elev| ≤ 30000`. The header promises FatalError on a contract violation (`biomes.hpp:19-22`), and the seams exist for tests and for P1-05/P1-06 reuse, so this should be a fatal error at the seam rather than UB.

Fix (for the engineer): check each rule field against its schema range in `compile_rule` (or once in `biome_definitions_from` and at the top of `biome_rule_matches`), fatal outside it, e.g. `if (r.elev_min_m < 0 || r.elev_min_m > BIOME_ELEV_MAX_M || r.elev_max_m < 0 || r.elev_max_m > BIOME_ELEV_MAX_M) fatal("biomes: rule elevation bound outside [0, 3000]");`, and likewise the temperature, rain, slope, hand and coast bounds (the constants already exist in `biomes.hpp:46-58`). `checked_mul` on the two products would also do, but range checks state the overflow argument of spec section 7 in code. The test writer can add one fatal-path test (`elev_min_m = 2^61`).

### Notes

**N1. B3/B4/B5 in G6 row blocks: no dependence on thread count or partition.** `biomes.cpp:391-413` (B3 and B4) and `:341-350` (B5). The row blocks are fixed by the height alone (`geo/blocks.hpp:22-51`, 64 rows per block). Each block reads only shared, immutable inputs: the eight input spans, the global `hand` vector (finished by G7 before the parallel region, `:378-383`), the compiled lookup (built once, `:385`), the two noise keys, and the elevation of neighbouring rows for G8 (`cell_slope_s2`, read only). Each block writes only `b4[i]` of its own rows (distinct `uint8_t` objects, so no data race under the C++ memory model). B5 runs after the whole B4 region has joined, reads `biome` (the B4 vector, never written in B5) and writes a separate copy `out` (`:338`), only at river cells of its own rows. Mode with ties to the smallest code (`river_cell_biome`, `:169-196`): a count of each candidate over all dry neighbours, chosen by (count, then smaller code), so neighbour order cannot matter; the reference in section 4 visits neighbours in reverse order and agrees. ThreadSanitizer at 5 threads is clean, and threads 1, 2, 3, 5 and 8 give identical files on GCC and Clang (section 4).

**N2. Jitter (B3) is location-keyed fixed point.** `biomes.cpp:298-311, 386-408`. `K_tj` and `K_rj` are `stream_key(seed, "geo.biomes.temp_jitter")` and `"geo.biomes.rain_jitter"` (`streams.hpp:60-64`, registered in `all_stream_names`), used only as `fbm_m` noise keys at X = `from_int(16x + 8)`, Y = `from_int(16y + 8)`: no `Rng`, no draw order. `from_ratio(temperature, 10)` and `mul` round half away from zero symmetrically (P0-01 5.2, 5.4) and are fatal on overflow, so negative temperatures and negative noise round identically on every compiler; `max(Fx{}, ...)` is a raw comparison. River cells (water 1) get B3 and B4 too, as the spec says, and B5 then decides; ocean and lake cells skip B3, which changes nothing since noise is position-determined. Resume equality: the layer recomputed from the stored inputs equals the stored layer on all five sweep worlds at every thread count (section 4).

**N3. Rule lookup order and the sort keys.** `biomes.cpp:206-250`. `std::stable_sort` by `code`, then a fatal check that adjacent codes differ (`:218`); `land_order` `stable_sort` by descending `priority`, then a fatal check that adjacent priorities differ (`:244-248`). So both orders are strict total orders on every path, including definition sets built directly in tests, which bypass the loader's named checks: a duplicate there is fatal, not an order left to the sort. Duplicate `key`s in a hand-built set are not checked here; they would hit the UNIQUE constraint in `write_biome` (fatal), never a silent order. `blighted_waste` (priority 0, not fallback) is never in `land_order` and never `fallback_code`, so B4 cannot assign it (`:227`, `:230-233`); the five sweep worlds' `biome_share` show `blighted_waste:0.0000`. The `uint8_t` casts of codes (`:148`, `:223`, `:226`, `:232`) happen after the 1..254 check at `:218` (same loop iteration, before the cast), so they are value-preserving.

**N4. Rain scale and sentinels.** `biome_rain_scale` (`:280-287`) selects on `max(W, H)` (`:385`, `int32` to `int64`, exact) with the total rule of B4. `biome_rain_bound` is `mul_int(scale, b)`, an exact raw product (≤ 4 × 2^32 × 10^4 < 2^48), fatal on overflow; the shipped scales 1.125, 1, 0.875 are binary fractions, but the comparison is exact for any scale, since rq is compared with the raw product and nothing is rounded. The sentinel widening (`:106-121`) turns a skipped comparison into a comparison against `Fx::MIN`, `Fx::MAX`, `INT64_MIN` or `INT64_MAX`; those values are only ever compared (`:123-128`), never added or multiplied, so the extremes cannot overflow. Sentinel equality is a raw comparison with `Fx::from_int(-60)` etc., exact. The random comparison against a naive `__int128` evaluation (section 4: 3,000,000 rules, extremes included) found no difference.

**N5. G7 and G8 are exact and order-free.** `terrain.cpp:54-111` (G7), `:113-165` (G8).
- G7: the drain set is found in index order and pushed in that order; the FIFO is a vector read from `head` while appending (`:84-98`), so it is a true FIFO in push order, with no pointer or hash order. Each non-drain cell has one `flow_dir`, so it can be reached only from its single downstream cell and `drain[m] = drain[c]` has exactly one possible value: the result is a function of the layers whatever the visiting order, as the spec says. `flow_dir` codes above 7 never equal `opposite(code)` (0..7), so they are unreached, as are steps off the grid and cycles. The minimum-class rule is `is_drain_cell` (`drainage.hpp:34-37`): water 2 or 3, or water 1 with `river ≥ k`, compared in `int64`. Fatal cases: k outside 1..15 (before the size check), wrong sizes, then one pass in index order (`:100-109`) that reports the lowest cell that is either unreached or negative, with a locale-free decimal formatter (`:24-36`). An independent recursive reference (section 4) agreed on 60,000 random fixtures, including the exact message of every fatal case, and on the five real worlds with k = 3 and k = 1.
- G8: `e' = max(e, 0)` in `int64`, `|gx|, |gy| ≤ 65534`, `S2 < 2^33`, no floating point. `slope_s2_limit` returns the high word of `(320 t.raw)^2` (`U128`, `mul_u64_wide`); for an integer S2 ≥ 0, `S2 × 2^64 ≤ X ⟺ S2 ≤ floor(X / 2^64) = X.hi`, exactly, so the threshold is exact for every legal tangent; `raw ≤ UINT64_MAX / 320` is checked; the clamp to `INT64_MAX` (`:156-158`) cannot trigger below t ≈ 2^25. Checked against `__int128` for every raw value 1..2,000,000, the 2,000,001 raw values ending at 100.0 and 5,000,000 random raw values in (0, 100]: `limit` passes and `limit + 1` fails in every case. Signed/unsigned: `t.raw()` is checked non-negative before the conversion to `uint64` (`:146-150`).

**N6. Loader: kind-level checks, the `biome` kind in the content hash, file order.** `content.cpp:705-746`, `kinds.cpp:81-278`, `schema.hpp:199-223`.
- The two `std::map<std::int64_t, std::size_t>` (`kinds.cpp:139`, `:202`) are ordered and used only for lookup of the first index; no unordered container is in the change (`grep unordered` over the diff: none). The checks receive the type-valid, non-duplicate definitions in ascending id by bytes (`candidates` are `stable_sort`ed with `bytes_less`, `content.cpp:704`) and report errors through `ErrorList`, which is sorted once by `error_less` over every field (`load_error.cpp:39-46`), so the error list is the canonical order of P0-03 9 on every platform whatever the order of the checks.
- The `biome` kind joins the registry by sorted name (`schema.cpp:365-367`); its definitions are encoded in ascending id with fields in schema declaration order (`biome_schema`, `kinds.cpp:233-254`), the rules array in array order and each rule's fields in declaration order (`biome_rule_schema`), `colour` as an `int64` like every int field. The hex literals of the TOML files are integers to the parser, so `0x183878` and `1587320` encode the same.
- File discovery: the eight files and the four `worldgen/` files were copied into data roots written in forward and in reverse order, on tmpfs (where `readdir` returned the reverse of creation order) and on ext4 (hashed order); the world files of 512 seeds 0 and 42 are identical to those from `game/data` in all four roots (section 4).

**N7. Database: schema 3, row order, rollback, page layout, climate row.** `db/schema.hpp:49-67`, `writer.cpp:410-420, 470-517, 596-604`, `climate.cpp:518-525`.
- DDL in the order meta, layer, pass, biome, climate (`DDL_STATEMENTS`); `SCHEMA_VERSION` 3. The empty world (`--until none`) is 32768 bytes, 8 pages, with root pages 2 `meta`, 3 `layer`, 4 `sqlite_autoindex_layer_1`, 5 `pass`, 6 `biome`, 7 `sqlite_autoindex_biome_1`, 8 `climate`, as P0-02 amendment 15 says; `user_version` 3.
- `write_biome` requires strictly ascending ids ≥ 1 (`:474`) and `biome_table_rows` emits ascending code (`biomes.cpp:420-432`); `write_climate` requires id 1 and one row. The rollback in `~StageWriter` restores `last_biome_id` and `climate_written` from the values saved at `begin_stage`, exactly as for `next_pass_id` (`:415-419`, `:599-603`). No timestamps, no row count or id from SQLite feeds back into output.
- The UNIQUE autoindex on `biome.key`: the final file is produced by `VACUUM INTO` (`writer.cpp:693`) from the working database. With the vendored SQLite and the pinned compile options (`extern/CMakeLists.txt`, SQLITE CONFIGURATION) and runtime pragmas (`runtime_settings.hpp:23-31`), a small C driver built the schema-3 tables and inserted the eight biome rows ascending, descending, and ascending after inserting and deleting 2000 unrelated rows in the same tables; the three `VACUUM INTO` files are byte-identical (16384 bytes each). So the index b-tree of the final file depends on its content, not on insertion order or earlier page churn, and in the generator the order is fixed anyway. Prior activity in the process: a driver generated 512 seed 13, then seed 42, then an `--until climate` world, then seed 42 again in one process; both seed-42 files equal the CLI's file byte for byte (section 4).
- Tables present in every world: `--until hydrology` has both tables empty, `--until climate` one `climate` row `(1, 6)` and no `biome` rows, a full run 8 `biome` rows and `(1, 6)` for seed 42. The climate stage writes its row after its two layers (`climate.cpp:518-525`), computing the wind again with `climate_wind(seed, weights)`, a pure function of the seed (one `Rng` on `geo.climate.wind`, one `weighted_index`) equal to the C2 value used for the layers. Every layer except `biome` (elevation to rainfall) has the same layer hash in the 0.7.0 world (`main070-a37c` build, `main`'s data) and the 0.8.0 world for 512 seed 42 (`hash --detail`); the `layer` table hash differs only by the added row.
- `inspect/`: tables are listed `ORDER BY name COLLATE BINARY` and rows read `ORDER BY` the primary key (`reader.cpp:639-640, 713-721`), so `biome` is checked before `climate`, rows in ascending id, and the corrupt-row reason is the first failing check in the spec's order (`geography.cpp:1176-1221`). The layer check (`:1223-1249`) reports the lowest cell index. `biome_share` iterates a `std::map` keyed by id (`:1251-1290`) and prints with `ratio4` and `escape_report_text` (no locale, no `printf`); `biome_patches` uses `label_components` with `Connectivity::eight` and `equal_key` = the biome value (`:1286`), G2's labelling, whose count does not depend on visiting order. The palette and composite build a 256-entry colour table from the table rows with magenta for missing ids (`render.cpp:263-272, 507-519, 800-815`), integer shifts only.

**N8. `p1-worlds.txt` still holds the 0.7.0 hashes.** `worldgen/tests/golden/p1-worlds.txt` is unchanged by the branch, so `world-hashes.sh expect` fails the four geo cases (for example `geo-seed-42-512` expects `5baf3bae…`, the hash of the 0.7.0 world, and gets `7bc71931…`). This is not a determinism defect: spec 10.4 says the biomes merge re-records the file, and the comparison across presets passes, which is the condition for recording. The validation specialist records the 0.8.0 values (and `p1-04-biomes.txt`) before merge; CI's `expect` step reports a failure until then.
