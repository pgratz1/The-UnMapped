# gdext

The C++ GDExtension of The Unmapped (design doc section 10): `world.db` readers bound into Godot, and the world viewer's logic. Later it will hold runtime generators and gameplay. Owned by the viewer engineer; started in phase P2.

It links `worldgen` through its public headers and nothing else of it; `worldgen` and `worldgen-cli` never depend on it (hard rule 2). All logic is C++; the Godot project in `game/` holds layout only (hard rule 3).

| What | Version | Where |
| --- | --- | --- |

**Why 4.7.2.** The design doc (section 10) pins Godot to the newest stable version that the Terrain3D plugin supports. Checked on 2026-11-15:

- Terrain3D's newest release is **v1.1.0-stable** (2026-10-30, https://github.com/TokisanGames/Terrain3D/releases/tag/v1.1.0-stable). Its release notes, under "Requirements", say: "Supports Godot 4.5-4.8+." Terrain3D's installation guide (https://terrain3d.readthedocs.io/en/1.1/docs/installation.html) defers to the release notes: "See the release notes for each version to learn which versions of Godot are supported."
- Godot's newest stable release is **4.7.2-stable** (2026-08-18, https://github.com/godotengine/godot/releases/tag/4.7.2-stable). 4.8 is at beta 3 (2026-11-09, https://github.com/godotengine/godot-builds/releases), so it is not a candidate.
- So the newest stable Godot that Terrain3D supports is 4.7.2.

**Why godot-cpp 10.0.0.** Since version 10, godot-cpp is versioned separately from Godot. Its README (https://github.com/godotengine/godot-cpp/blob/10.0.0-stable/README.md) says: "Using the `api_version` parameter (see below), godot-cpp v10 can target Godot 4.3 or later", and "GDExtensions targeting an earlier version of Godot should work in later minor versions, but not vice-versa." 10.0.0-stable (2026-09-15) is its newest release and ships `extension_api-4-7.json`. That file equals the API dumped from the pinned 4.7.2 editor in every section except the version header, and the interface JSON is byte-identical (`extern/README.md`, Notes). Terrain3D v1.1.0 itself builds against a godot-cpp master commit from 2026-03 (submodule `60b5a419`), so it does not pin a godot-cpp tag that we could share.

Terrain3D v1.1.0-stable is vendored in `extern/terrain3d/` and built by our CMake against godot-cpp 10.0.0 with a force-included compatibility header and one edited line (`extern/README.md`); it is used by the 3D terrain preview ("Terrain preview" below).

## Getting the pinned editor

The build never downloads anything. Install the editor once into the tools folder under the build root (Paul approved this location) with the fetch script, from the repository root (on Windows, from Git Bash):

```
tools/ci/fetch-godot.sh
```

It installs into `~/.cache/the-unmapped/tools/godot-4.7.2-stable/` on Linux and `%LOCALAPPDATA%\the-unmapped\tools\godot-4.7.2-stable\` on Windows, after checking the downloaded archive and each extracted file against the SHA-512 digests pinned in `tools/ci/godot-4.7.2-stable.sha512` (the archive digests are the release's `SHA512-SUMS.txt`; the GitHub asset SHA-256 digests are `cadd3204e728a35d3f13adb7fd0d7902636b79f6b95c40c265eb73b6c35329e4` for `Godot_v4.7.2-stable_linux.x86_64.zip` and `731980f9608d61333e5baf54a2ef17210acc7a538446c0cb9969f002aca1e953` for `Godot_v4.7.2-stable_win64.exe.zip`). An installed, matching copy is left alone. CI uses the same script (CLAUDE.md, "Continuous integration"). The Windows zip holds `Godot_v4.7.2-stable_win64.exe` and `Godot_v4.7.2-stable_win64_console.exe`; the console one prints to the terminal and is the one the headless check uses.

CMake looks for the editor there, then on `PATH`; `-DUNMAPPED_GODOT=<path>` or the environment variable `UNMAPPED_GODOT` names another copy. It must report version `4.7.2.stable`, or the headless check is not registered.

## Building

The extension is the CMake option `UNMAPPED_BUILD_GDEXT`, **OFF by default**. With it off, the build is exactly as without `gdext/`. Turn it on for any non-sanitizer preset:

```
cmake --preset linux-gcc-debug -DUNMAPPED_BUILD_GDEXT=ON
cmake --build --preset linux-gcc-debug
ctest --preset linux-gcc-debug
```

The option is cached, so later builds of that tree keep it. To keep a tree without the extension next to one with it, give the second its own directory, e.g. `-B ~/.cache/the-unmapped/build/<source dir name>/linux-gcc-debug-gdext`, and use `cmake --build <dir>` and `ctest --preset linux-gcc-debug --test-dir <dir>`.

With the option on:

- godot-cpp is built as a vendored target (warnings suppressed, the project's floating-point flags applied). Its bindings are generated by Python 3 into the build tree.
- `worldgen` and SQLite are built position independent (`CMAKE_POSITION_INDEPENDENT_CODE`), since they are linked into a shared library. This does not change any integer result; `tools/ci/world-hashes.sh` gives the same hashes with the option on and off.
- `unmapped_gdext` is a project target (`unmapped_project_target()`, warnings as errors).

Requirements in addition to the usual ones: Python 3.8 or newer (to generate the bindings).

Clean build times measured on a 6-core Linux machine without ccache (2026-11-15). godot-cpp adds about 1,100 compile steps (its generated bindings) to the build's roughly 90:

| Build | Extension off | Extension on |
| --- | --- | --- |
| `linux-gcc-release` | 48 s | |
| `linux-clang-release` | 32 s | 189 s |
| `linux-gcc-debug` | | 165 s |

Configure takes about a second more (the binding generator lists its files). A rebuild after changing only `gdext/` takes seconds. ccache, used automatically when installed, caches godot-cpp like everything else, so a later clean build of an unchanged godot-cpp is much faster.

The sanitizer preset `linux-clang-asan` refuses the option at configure time: an instrumented library cannot be loaded into the uninstrumented editor, Clang does not link the sanitizer runtime into a shared library (the link fails on `__asan_*` symbols), and godot-cpp's `defs.hpp` refuses sanitizer builds unless Godot's own `ASAN_ENABLED`/`UBSAN_ENABLED` macros are set. Sanitizing the extension would need a sanitized Godot build; not planned.

## How the project finds the extension

Godot loads an extension from a `.gdextension` file inside the project, and writes its cache (`.godot/`) inside the project. To keep both the library and the cache out of the repository (it may sit in a synced folder), Godot never runs on `game/` itself but on a **run copy** that the build assembles under the build tree:

```
<build>/game/                     e.g. ~/.cache/the-unmapped/build/<source dir>/<preset>/game/
  project.godot        -> <repo>/game/project.godot
  unmapped.gdextension -> <repo>/game/unmapped.gdextension
  viewer/              -> <repo>/game/viewer/
  ...                     one link per entry of game/
  bin/                    real folder: the extension's output directory
    libunmapped_gdext.so  (Windows: unmapped_gdext.dll)
  .godot/                 real folder: Godot's cache
  addons/terrain_3d/      real folder, only with -DUNMAPPED_BUILD_TERRAIN3D=ON (spec V3D-01 3.4)
    terrain.gdextension   generated from gdext/terrain3d/terrain.gdextension.in
    bin/libterrain3d.so   (Windows: terrain3d.dll), the plug-in's output directory
```

- The library is built straight into `<build>/game/bin/`. `game/unmapped.gdextension` names it as `res://bin/libunmapped_gdext.so` (Linux) and `res://bin/unmapped_gdext.dll` (Windows), relative to the project, so the committed file is the same on every machine.
- After each build of the library, `gdext/cmake/assemble_project.cmake` makes one link per entry of `game/` (new files appear without reconfiguring; links to deleted entries are removed) and writes `.godot/extension_list.cfg`, so the viewer runs straight after a build.
- Links: symbolic links on Linux. On Windows, folders are directory junctions (no administrator rights or Developer Mode needed); files are symbolic links where Windows allows them, else hard links, else copies (with a warning). **Not yet tried on Windows.**
- Each build tree has its own run copy, so several presets and worktrees never share a library or a cache.
- The editor edits the repository's files through the links: scenes saved in `viewer/` land in `game/viewer/`.
- One caveat: when the editor saves a file at the project root (in practice `project.godot`, from Project Settings) with "safe save" on, it writes a temporary file and renames it over the link, so the run copy gets a real file and the repository copy is not updated. The next build notices that the file differs from the repository's and warns, without overwriting it; copy the change across by hand. Project settings are rarely changed and are best edited in `game/project.godot` directly.

Do not open `game/project.godot` itself in the editor: the extension is not there (no `bin/`), and the editor would create `game/.godot/` in the repository.

### Markers in the viewer (spec P4-04 Part B)

- **Model.** `HistoryState` builds worldgen's `MarkerIndex` once, after `load_history`; a failure leaves the history loaded and the markers unavailable, and the file label gains `markers: <code>: <message>`. It holds the options (old ruins off, event places on, passes on, sites on), the enabled flag (on) and the current `YearMarkers`. On a year change (after the territory image, before the legend), an option change or the flag, it computes `markers_at` into a scratch set and swaps it in only when the sites, settlements, places or passes differ (the year alone is no difference); only then does the model emit `markers_changed`. Bound: `get_markers_available()`, `get_markers_enabled()` / `set_markers_enabled(on)`, `get_marker_option(name)` / `set_marker_option(name, on)` (`faded`: old ruins, P5-06 25.1 (e); `events`, `passes`, `sites`: worldgen's `MarkerOptions::sites`, mines and towers; `mines` is still accepted), `get_markers()` (in the draw order of 6.1: `{type, id, x, y, glyph, fill, capital, small, events}`; P5-04 11.3: the mines, type `site`, glyph `mine`, fill (60, 60, 60), small, between the ruins and the standing settlements, with `offset_x` 7 and `offset_y` -7; P5-06 11.4: towers, type `site`, glyph `tower`, fill (120, 60, 180), offset from worldgen's `site_glyph_offset`: a library (-7, -7), a tower in the wild (0, 0); every site entry carries `site_kind`); settlements are typed by worldgen's `settlement_marker_type`, so a ruin 1,500 years old or more (`OLD_RUIN_YEARS`) is of type `faded`, drawn with the faded glyph only with the option, `get_marker_glyph(name)` (`{radius, cells}` from worldgen's `marker_glyph`), `describe_marker(index)` (the hover texts of 8.5; sentences by worldgen's `render_event`; a ruin or faded ruin without a ruin event ends `ruined in <R>: cause not recorded`, P4-05 F6) and `get_marker_legend()` (the last ring row is `any other event`, F7; the last rows `mine` and `tower` with the Sites box on; `old ruin` with the Old ruins box on). A mine's hover text is `<site name> (mine of <civilization>), since <origin year>` (P5-04 11.3); a tower's `<site name> (tower of <figure display name>), since <year>`, a library's `(library of ...)`, the figure being the `figure` participant of the site's `tower_founded` event (P5-06 11.4); an old ruin's `<name>, old ruin of a <kind>, ruined in <R>: <sentence>` (25.1 (e)). A held region's hover text ends `, ruled by <figure display name>` (`Timeline::ruler_at` at the shown year) or `, ruler unrecorded` (P5-06 12); a mine is drawn from its `origin_year` until (not including) its `ended_year`, so no closed mine is ever shown.
- **Screen.** The sidebar's Markers group (between the views and the meta panel): `%MarkersToggle` "Show markers" (key **M**), `%MarkFaded`, `%MarkEvents`, `%MarkPasses`, `%MarkSites` "Sites" (mines and towers; P5-04, P5-06; `%MarkFaded` reads "Old ruins") and the key list `%MarkerLegend` (its icons drawn at glyph cell 2 on a 23 px canvas, the ring rows at 1, so the pass chevron is 14 px; P4-05 F7), all disabled without markers. On `markers_changed` and `view_selected` the screen hands `get_markers()` and their glyphs to the map view, so markers show over every view; no marker is drawn into a view's image.
- **Drawing.** Glyphs are drawn at screen size: each glyph cell is g x g screen pixels, g = 1 below zoom 0.5 (screen pixels per cell), 2 below 10, else 3 (spec P4-05 12.1 F1; P4-04 had 1 below zoom 4), so at the fitted view of a 1024 map a hamlet is 14 px and a city 22, centred on floor(offset + (x + 0.5) zoom), a mine 7 glyph cells (7 g pixels) right and 7 up of that, so that its town does not hide it (as worldgen's `draw_markers` offsets it by `SITE_GLYPH_OFFSET` cells at scale 1); below zoom 0.5 hamlets, villages that are not capitals, ruins, faded ruins and mines are left out. Each distinct (glyph, fill, g) is one cached `ImageTexture` (dropped when the world closes), so a frame is one `draw_texture` per marker. Hover tests the glyph cells in reverse draw order (any class but none: a declining settlement's interior counts, the inside of a ring does not, so a settlement in a ring is hit); entries marked small (hamlets, villages that are not capitals, ruins, faded ruins, mines) and passes are also hit when the mouse is within one glyph cell (Chebyshev) of a non-zero cell (F6); while a marker is hit, the line under the map shows its description instead of the cell's.

### The browser of civilizations and events (spec P4-05 Part B)

- **Model.** `BrowserState` (`gdext/src/viewer/browser_state.hpp`, C++ only, no Godot types) is built when a world opens, after the history and the markers: worldgen's `BrowserIndex` (`worldgen/inspect/history_browser.hpp`) and the row text of every event (`row_text`). A failure leaves history and markers working, the browser unavailable and the file label with a line `browser: <code>: <message>`. The bound methods of spec 5.2 are in `viewer_model_browser.cpp`: `get_browser_available()`, `get_civilization_list()`, `get_civilization_block(c)` (links in characters, targets the report's tags `c3`, `s12`, `rg4`, `ra2`, `e57`), `get_event_ids()`, `get_event_rows()`, `get_event_detail(e)`, `set_browser_scope|group|level|years|this_year`, `select_civilization(c)`, `select_event(e)`, `select_place(type, id)`, `clear_selection()`, `follow_link(target)` (`c`, `s`, `rg`, `e`; `can_follow_link`), `browser_back()`, `browser_forward()`, `set_follow(on)`, `follow_first()`, `search_names(q)`, `get_selection()`, `get_highlight()`, plus `get_event_groups()` (the group words in code order; the group menu is built from it, so a new group needs no viewer change), `get_place_text()`, `get_event_row_at_year(y)` and `get_region_at(x, y)`; signals `browser_selection_changed`, `event_list_changed`, `highlight_changed`. With follow on and a list that is not empty, `step_event` (the year bar's event buttons, Page Up / Page Down) walks the list (spec 5.3); a follow step does not push the path, a selection does. The highlight of a selected civilization (the regions it holds at Y and its standing marker entries) is recomputed on each year change and emitted only when it differs; the dimming mask (one byte per cell from layer `region`) is rebuilt only when the held set changes.
- **Screen.** A third pane `%RightPane`, a `TabContainer` with the tabs **Browser** and **Legend** (the legend moved there unchanged; a world without history opens on Legend with Browser disabled). Browser: `<` / `>` (path), the search field (`search_names` on every change, results replacing the civilization list), the civilization list (swatch, name, race, years, fate), the event filters (scope All / Selected / Place, the kind group (worldgen's groups in code order from `ALL_GROUPS`, so P5-04's `alliances` is last; `--browser-group alliances` picks it), **All events** = level full for both the list and the block), the years (from, to, This year), **Follow** (`%FollowToggle`, a `CheckBox`) and **First** (`%FollowFirst`) (the first event of the list), the event list (one row per event, the full row as tooltip; a year change scrolls it to the year without rebuilding it) and the detail (a `RichTextLabel` built with `push_meta` / `add_text` / `pop`, never BBCode; a click on a link follows it). The detail shows the selected event (its row with linked names, place, kind and salience, participants, values, causes and effects as links), else the selected place (its hover text, then the list holds its events), else the selected civilization's block as the report prints it. The map draws, after the image: the dimming of the land the selected realm does not hold (black at alpha 0.45, as tiles like the image), the markers, gold frames around the realm's settlements and a cyan one around a selected settlement, and two squares around the selected event's place. A click on the map (press and release within 4 px) selects: a settlement marker its settlement, a ring its smallest event, a region cell its region.
- **Keys** (when no text field or list has focus): **F** follow on / off, **Backspace** / **Shift+Backspace** back / forward, **Escape** releases the focus of any control that has it (P4-06 8.2; P4-05: of a browser control) or else clears the selection, **Ctrl+F** the search field, **B** hides or shows the right pane, Page Up / Page Down the event steps (follow-aware).
- **Performance** (spec 7; `--bench` prints it: the index and row texts at open, filter changes to full / all with the model's select and the list rebuild, `select_civilization` and `select_event`, the browser steps (i) to (k) of each year change, the `event_list_changed` and `highlight_changed` counts over 0 to E and back with the first civilization selected and follow on, and the slowest mask rebuild). ### The history movie (spec P4-06)

- **Model.** `PlaybackState` (`gdext/src/viewer/playback_state.hpp`, C++ only, no Godot types) holds the session: state (`stopped`, `playing`, `paused`, `ended`), span [P0, P1], speed (1, 2, 5, 10, 20, 50, 100, 200, 500 years a second; default 10), skip quiet years (default on: a year that is not a stop year takes a tenth of the dwell D = 1,000,000 / speed microseconds), the stop years, the year and the microseconds spent at it, the session clock, the ticker (at most 6 entries) and the flashes (at most 32, 1.2 s each). Its only time source is `advance(dt)`; one call changes the year at most once and never passes a stop year (spec 4.2; runs of quiet years are passed arithmetically). The model (`viewer_model_playback.cpp`) hands it the playback list L (the browser's filter with the year span open and This year off, worldgen's `select`), the timeline's holder-change years and the phase marks; the stop years are L's years in the span, with scope all also the holder changes and phase starts, plus P0 and P1. The ticker's texts are the browser's row texts and the phase marks' labels; a flash is at `MarkerIndex::event_place` in `event_symbol_colour` of the kind. A year change not made by playback (slider, keys, buttons, `select_event`, back / forward, a follow step) pauses at the new year, refills the ticker with that year's lines and clears the flashes; a selection or filter change recomputes the stops and keeps the span. Bound: `play(from, to)` (-1: that end of the default span: the list's first to last event year with scope entity or place, else [0, E]), `toggle_playback()`, `stop_playback()`, `playback_advance(usec)`, `get_playback()` (`{state, from, to, speed, skip_quiet, clock, stops}`; stopped: the default span), `get_playback_speeds()`, `set_playback_speed(s)`, `step_playback_speed(d)`, `set_playback_skip_quiet(on)`, `get_playback_stop_years()`, `get_ticker_lines()` (`{year, event, kind, text, current}`), `get_flashes()` (`{event, x, y, colour, age, life}`); signals `playback_changed`, `playback_finished`, `ticker_changed`. The command-line parser is the pure function `parse_play_options` in the same header.
- **Screen** (`viewer_screen_playback.cpp`). ### History in the viewer (spec P4-03)

- **Reading.** `ViewerModel::open_world` calls worldgen's `load_history` on the open file (`WorldFile::reader()`, C++ only; the extension issues no SQL). The history status is `none` (a world without history, `history_missing`, or no world open), `loaded` (Y = E, the present) or `failed` (any other error, with worldgen's code and message: the world still opens with its geography, the file label gains a line `history: <code>: <message>`, the year bar is disabled).
- **Methods** (bound): `get_history_status()`, `has_history()`, `get_history_error_code()`, `get_history_error_message()`, `get_end_year()`, `get_year()` (-1 without history), `set_year(y)`, `step_year(delta)`, `step_event(direction)`, `step_holder_change(direction)`, `has_previous_event()`, `has_next_event()`, `has_previous_change()`, `has_next_change()`, `get_year_info()`, `get_year_marks()`, `get_region_holding(region)`, `get_civilization_info(civ)`, `get_civilizations_alive()`, `get_territory_view()`. None throws into Godot.
- **The territory view.** With history and the composite `regions` available, the first composite is `territory`, so the world opens on it: worldgen's `render_territory` at Y (the same bytes as `worldgen-cli render --composite territory --year Y`). Its base is built on first display; a year change whose holders differ from the image's redraws it in place into the same `Image` (`view_image_changed`), so quiet years cost nothing. Its legend: the realms alive at Y under their race's plural, the two border rows and the free-land rows of `regions`.
- **The year bar** (`YearBar` in the scene): -25, -1, previous event, previous change of holder, the slider over the year marks, next change, next event, +1, +25 and a year field; under it the year readout and the counts of the year. Keys, when no text field has focus (`_unhandled_key_input`): Left / Right one year, Shift with them 25, Page Up / Page Down the previous / next event, `[` / `]` the previous / next change of holder, Home year 0, End the present. The year buttons, the slider and the map view take no keyboard focus (`focus_mode` none in the scene), so the arrow keys reach the year bar instead of moving focus; the layer list and the meta panel still take focus when clicked, and while one of them has it the arrow keys act on it.
- **Hover.** With history, the cell description of every view ends with `   |   held by <realm> since <Y>`, `   |   free since <Y>` or `   |   free` for the cell's region at Y.

Command line additions (after `--` with a world path): `--year <Y>` opens at year Y; `--faded` starts with the faded ruins shown; `--bench` times opening the world and a year change to every year 0 to E and back, prints the figures (`UNMAPPED-BENCH:` lines: open, first territory image, mean and slowest year change, then each step of a year change (spec P4-05 12.3) with its maximum, the year of it and its mean: (a) `year_state` and holders, (b) `render_territory` into the image, (c) the `view_image_changed` handler (the map's texture upload), (d) the marker step and the `markers_changed` handler, (e) the model's legend, (f) the screen's legend, (g) the year bar, (h) the rest of the `year_changed` handlers, the model part a + b + d + e and the whole `set_year`; the number of image redraws, the slowest and the map tiles uploaded, the marker steps and `markers_changed`), and quits. The viewer takes what it knows of the layer catalogue of spec P1-00 section 4 from worldgen's `worldgen/inspect/layer_catalogue.hpp` (spec P4-02; plain C++, model side): each layer's group, its unit, the display form of a value (`123.4 m`, `12.3 °C`, `lake`, `142 / 255`, `48 m offshore`, ...), the legend of each palette and composite and the composite's description, the composites a world can show (`available_composites`) and region names (`region_name` over the `RegionRecord`s of `read_region_rows`, which carry the name and biome). The extension keeps no copy of any of it and reads no column of table `region` itself. Legend colours are computed with worldgen's own palette functions and ramp stops, so each swatch is the colour drawn; the biome rows come from the world's table `biome`. Integers stay integers up to `WorldLayer`; floats appear only on the Godot side (zoom, pan) and never reach worldgen. The viewer lists whatever layers the file holds, so new layers appear without viewer changes; each is drawn with worldgen's palette for it (a new palette needs no viewer change either, unless, like `biome`, it needs data from a table). Composites appear when worldgen offers them for the file's layers.

## Terrain preview

The 3D terrain preview of specs `docs/specs/v3d-01-terrain-preview.md` and `v3d-02-biome-ground-and-vegetation.md`: a world's `elevation` layer as Terrain3D terrain at one vertex per 16 m cell (true scale, map centred on the origin, region size 256), lakes flat at their surface, an opaque sea plane at 0 m faded by depth fog to the horizon, and a fly camera. Since V3D-02 each biome has its own generated ground texture (grain, relief and roughness, coloured so that from afar it matches the 2D map), blended over about two cells at biome borders, rock on slopes over 35 degrees and snow on the coldest alpine ground, rivers painted as on the 2D composite map, and placeholder trees, shrubs, reeds and snags built in code and placed by Terrain3D's instancer from the world seed. `--flat-colours --no-trees` gives V3D-01's look: one white texture and the biome colours in the colour map. It is the scene `res://viewer3d/terrain_preview.tscn`; the 2D viewer (`viewer.tscn`, the main scene) is unchanged.

Code: `gdext/src/terrain/`. `terrain_data` (layout, height and colour buffers, cell and world coordinates, ground samples, the HUD line), `fly_state` (the camera rules of V3D-01 8.2), `ground` (the fifteen ground types, their 256 x 256 textures, the per-cell ground, the control map, the river paint and the textured colour map; V3D-02 3 to 5), `vegetation` (kinds, densities, the seeded placement and the instance cap; V3D-02 6; the forest types forest floor and carr carry 150 trees per hectare at full timber, Q8 983 against 393 elsewhere, with the same conifer share, and 100 shrubs per hectare of undergrowth, Q8 655, on top of their own shrubs: Paul, 2026-11-27; an instance's offset from its cell's vertex is two keyed draws, one per axis, over the whole 16 m cell, `cell_jitter`, where spec 6.4 has [-6, 6) m from one hash, which stood trees in rows 16 m apart) and `placeholder_meshes` (the flat-shaded meshes of V3D-02 6.2) are plain C++ without Godot types, built as the static library `unmapped_terrain_core` that the extension and the unit tests link. `TerrainPreview` opens the world through `WorldFile`, copies the buffers into three `Image`s (height and control `FORMAT_RF`, colour `FORMAT_RGBA8`) and creates the `Terrain3D` node through Godot's `ClassDB`: `unmapped_gdext` never links Terrain3D, so the class is used only when the plug-in is in the run copy, and without it the preview shows the sea plane and says so. The textures and the vegetation scenes (a `PackedScene` per kind built in code, children `MeshLOD0` and `MeshLOD1`) are made once per process; the instances go to the instancer with `add_transforms`, one instancer cell (512 m) per call, then one `update_mmis` rebuilds the multimeshes on the next drawn frame. `terrain_check` and `terrain_check_ground` are the check below.

### Building

The plug-in is the CMake option `UNMAPPED_BUILD_TERRAIN3D` (default OFF; configure refuses it without `UNMAPPED_BUILD_GDEXT=ON`). With it off, the build, the run copy (no `addons/`) and the test list are as before, apart from the preview's own sources and tests, which are built with the extension.

```
cmake --preset linux-gcc-release -DUNMAPPED_BUILD_GDEXT=ON -DUNMAPPED_BUILD_TERRAIN3D=ON
cmake --build --preset linux-gcc-release
ctest --preset linux-gcc-release -R gdext
```

The plug-in adds 15 sources to the build.

### Flying over a world

```
B=~/.cache/the-unmapped/build/$(basename "$PWD")/linux-gcc-release
GODOT=~/.cache/the-unmapped/tools/godot-4.7.2-stable/Godot_v4.7.2-stable_linux.x86_64
OUT=~/.cache/the-unmapped/out
"$B/tools/worldgen-cli/worldgen-cli" generate --seed 42 --map-size 1024 --out $OUT/seed42-1024.db
"$GODOT" --path "$B/game" res://viewer3d/terrain_preview.tscn -- $OUT/seed42-1024.db
```

Maps of 512, 1024 and 2048 cells are accepted. The camera starts above cell (N/2, 7N/8), 300 m above the highest peak, looking north at pitch -25. Keys: W/S forward and back along the view, A/D sideways, E/Q up and down, Shift x4, mouse wheel or `-`/`=` speed (10 to 2000 m/s), right mouse button held to look, arrow keys to turn, R back to the start, T vegetation on or off (the mesh assets' `enabled`; instances are kept), G ground textured or flat (reopens the world in the other mode and keeps the camera; nothing without a `biome` layer), H hides the HUD, Escape releases the mouse. "Open world..." opens another file. The HUD shows the cell, the position in metres east and south of the centre, the altitude and height above ground, the ground's elevation (and a lake's surface), the biome and region names, the speed and the frame rate.

Options after the world path: `--at <x> <y>`, `--alt <m>`, `--above <m>` (start that many metres above the ground at the start cell; not with `--alt`), `--heading <deg>`, `--pitch <deg>`, `--speed <v>`, `--size <w> <h>`, `--screenshot <file.png>` (saved 2 s after the first drawn frame after the terrain is added, then quit; needs a display), `--bench`, `--check <dir> --expect-terrain3d present|absent`, `--no-terrain3d`, `--flat-colours` (V3D-01's ground), `--no-trees` (no vegetation), `--instance-cap <n>` (0 to 4,000,000, default 2,000,000: above it the placement keeps a uniform, seeded share of every kind).

The status lines at the bottom left name the mode (`ground: textured, 15 ground types` or `ground: flat colours`), the vegetation (`vegetation: <n> instances`, with `, thinned from <S> to the cap` when the cap binds, or `vegetation: off`), and what is missing: `no biome layer: ground drawn grey, no vegetation`, `no water layer: rivers not drawn`, `no timber layer: tree density from the biome alone`, `no temperature layer: no snow`, `no seed in meta: vegetation placed with seed 0`. A top-down view to compare with the 2D map: `--at 512 512 --alt 22000 --pitch -89 --screenshot $OUT/top.png` on a 1024 world, against `worldgen-cli render --db <world> --composite biomes`.

### Checks

- `gdext-terrain-tests` (doctest, no Godot; built with the extension and tests): U1 to U6 of V3D-01 9.1 and U7 to U16 of V3D-02 11.1 (ground types; the textures against the test's own copy of the formula and recorded FNV-1a hashes, which must pass on GCC, Clang and MSVC alike; `hash32` and `mix64` vectors; control on hand-made grids; river paint against the 2D rule; the textured colours; placement repeatability, exclusions and counts per kind within 4 standard deviations; the cap against a brute-force sort; `ground_low`; the meshes' triangle counts, normals, winding and heights).
- `gdext-terrain-check` (registered with `gdext-headless-check`, Terrain3D on or off; `gdext/cmake/terrain_check.cmake`, about 14 s): generates a 512 world (seed 49) and a 1024 world (seed 1) with `--until regions` and renders their `biome` layer and `map` composite, a 512 world with `--until elevation` and the test pattern, then runs the preview headless with `--check`: the 512 world in the default mode, with `--flat-colours --no-trees` and with `--no-terrain3d`, the 1024 world with `--instance-cap 50000`, and the two others. V3D-01's T1 to T8: layout and images; every height against the check's own formula; every colour against `biome.png` (flat colours); the start and the HUD at four places; with Terrain3D its region locations and `get_height` and `get_color` at 32 points; without it, the status, sea and camera; 300 frames of scripted flight above the ground. V3D-02's T3 and T9 to T16, with the check's own copy of the ground, river, control and colour formulas and of the exclusion and cap rules: the colour image, and every painted river cell against `map.png`; the fifteen texture assets (images equal to `build_ground_texture`, `albedo_color`, `uv_scale`); the control image and `get_control` at 32 points; the five mesh assets and their LODs; the instances stored in the regions per kind and the first and last of each at their place; the placement and the cap; the sea plane, far plane and fog; the status lines; keys T and G. Key T makes Terrain3D log `_viewport_texture is null. Couldn't create thumbnail picture` once per mesh asset under `--headless` (it redraws an editor thumbnail when `enabled` changes); the check passes regardless. Terrain3D instantiates and answers `get_height` and `get_color` under `--headless`, so T6 runs in CI. Both Godot checks hold `RESOURCE_LOCK godot-run-copy`, since both import the same run copy.
