# gdext

The C++ GDExtension of The Unmapped (design doc section 10): `world.db` readers bound into Godot, and the world viewer's logic. Later it will hold runtime generators and gameplay. Owned by the viewer engineer; started in phase P2.

It links `worldgen` through its public headers and nothing else of it; `worldgen` and `worldgen-cli` never depend on it (hard rule 2). All logic is C++; the Godot project in `game/` holds layout only (hard rule 3).

## Pinned versions

| What | Version | Where |
| --- | --- | --- |
| Godot editor | **4.7.2-stable** (`4.7.2.stable.official.ed1daf0bf`) | Downloaded into the tools folder under the build root, see below; not in the repository |
| godot-cpp | **10.0.0-stable**, built for API **4.7** | Vendored in `extern/godot-cpp/` (`extern/README.md`) |
| `.gdextension` `compatibility_minimum` | `4.7` | `game/unmapped.gdextension` |

**Why 4.7.2.** The design doc (section 10) pins Godot to the newest stable version that the Terrain3D plugin supports. Checked on 2026-11-15:

- Terrain3D's newest release is **v1.1.0-stable** (2026-10-30, https://github.com/TokisanGames/Terrain3D/releases/tag/v1.1.0-stable). Its release notes, under "Requirements", say: "Supports Godot 4.5-4.8+." Terrain3D's installation guide (https://terrain3d.readthedocs.io/en/1.1/docs/installation.html) defers to the release notes: "See the release notes for each version to learn which versions of Godot are supported."
- Godot's newest stable release is **4.7.2-stable** (2026-08-18, https://github.com/godotengine/godot/releases/tag/4.7.2-stable). 4.8 is at beta 3 (2026-11-09, https://github.com/godotengine/godot-builds/releases), so it is not a candidate.
- So the newest stable Godot that Terrain3D supports is 4.7.2.

**Why godot-cpp 10.0.0.** Since version 10, godot-cpp is versioned separately from Godot. Its README (https://github.com/godotengine/godot-cpp/blob/10.0.0-stable/README.md) says: "Using the `api_version` parameter (see below), godot-cpp v10 can target Godot 4.3 or later", and "GDExtensions targeting an earlier version of Godot should work in later minor versions, but not vice-versa." 10.0.0-stable (2026-09-15) is its newest release and ships `extension_api-4-7.json`. That file equals the API dumped from the pinned 4.7.2 editor in every section except the version header, and the interface JSON is byte-identical (`extern/README.md`, Notes). Terrain3D v1.1.0 itself builds against a godot-cpp master commit from 2026-03 (submodule `60b5a419`), so it does not pin a godot-cpp tag that we could share.

Terrain3D is not integrated now; it only decides the version (milestone 2 confirms it).

## Getting the pinned editor

The build never downloads anything. Install the editor once into the tools folder under the build root (Paul approved this location) with the fetch script, from the repository root (on Windows, from Git Bash):

```
tools/ci/fetch-godot.sh
```

It installs into `~/.cache/the-unmapped/tools/godot-4.7.2-stable/` on Linux and `%LOCALAPPDATA%\the-unmapped\tools\godot-4.7.2-stable\` on Windows, after checking the downloaded archive and each extracted file against the SHA-512 digests pinned in `tools/ci/godot-4.7.2-stable.sha512` (the archive digests are the release's `SHA512-SUMS.txt`; the GitHub asset SHA-256 digests are `cadd3204e728a35d3f13adb7fd0d7902636b79f6b95c40c265eb73b6c35329e4` for `Godot_v4.7.2-stable_linux.x86_64.zip` and `731980f9608d61333e5baf54a2ef17210acc7a538446c0cb9969f002aca1e953` for `Godot_v4.7.2-stable_win64.exe.zip`). An installed, matching copy is left alone. CI uses the same script (CLAUDE.md, "Continuous integration"). The Windows zip holds `Godot_v4.7.2-stable_win64.exe` and `Godot_v4.7.2-stable_win64_console.exe`; the console one prints to the terminal and is the one the headless check uses.

CMake looks for the editor there, then on `PATH`; `-DUNMAPPED_GODOT=<path>` or the environment variable `UNMAPPED_GODOT` names another copy. It must report version `4.7.2.stable`, or the headless check is not registered.

## Building

The extension is the CMake option `UNMAPPED_BUILD_GDEXT`, **OFF by default**. With it off, the build is exactly as without `gdext/`. Turn it on for any non-sanitizer preset:

```
cmake --preset linux-gcc-debug -DUNMAPPED_BUILD_GDEXT=ON
cmake --build --preset linux-gcc-debug
ctest --preset linux-gcc-debug
```

The option is cached, so later builds of that tree keep it. To keep a tree without the extension next to one with it, give the second its own directory, e.g. `-B ~/.cache/the-unmapped/build/<source dir name>/linux-gcc-debug-gdext`, and use `cmake --build <dir>` and `ctest --preset linux-gcc-debug --test-dir <dir>`.

With the option on:

- godot-cpp is built as a vendored target (warnings suppressed, the project's floating-point flags applied). Its bindings are generated by Python 3 into the build tree.
- `worldgen` and SQLite are built position independent (`CMAKE_POSITION_INDEPENDENT_CODE`), since they are linked into a shared library. This does not change any integer result; `tools/ci/world-hashes.sh` gives the same hashes with the option on and off.
- `unmapped_gdext` is a project target (`unmapped_project_target()`, warnings as errors).

Requirements in addition to the usual ones: Python 3.8 or newer (to generate the bindings).

Clean build times measured on a 6-core Linux machine without ccache (2026-11-15). godot-cpp adds about 1,100 compile steps (its generated bindings) to the build's roughly 90:

| Build | Extension off | Extension on |
| --- | --- | --- |
| `linux-gcc-release` | 48 s | |
| `linux-clang-release` | 32 s | 189 s |
| `linux-gcc-debug` | | 165 s |

Configure takes about a second more (the binding generator lists its files). A rebuild after changing only `gdext/` takes seconds. ccache, used automatically when installed, caches godot-cpp like everything else, so a later clean build of an unchanged godot-cpp is much faster.

The sanitizer preset `linux-clang-asan` refuses the option at configure time: an instrumented library cannot be loaded into the uninstrumented editor, Clang does not link the sanitizer runtime into a shared library (the link fails on `__asan_*` symbols), and godot-cpp's `defs.hpp` refuses sanitizer builds unless Godot's own `ASAN_ENABLED`/`UBSAN_ENABLED` macros are set. Sanitizing the extension would need a sanitized Godot build; not planned.

## How the project finds the extension

Godot loads an extension from a `.gdextension` file inside the project, and writes its cache (`.godot/`) inside the project. To keep both the library and the cache out of the repository (it may sit in a synced folder), Godot never runs on `game/` itself but on a **run copy** that the build assembles under the build tree:

```
<build>/game/                     e.g. ~/.cache/the-unmapped/build/<source dir>/<preset>/game/
  project.godot        -> <repo>/game/project.godot
  unmapped.gdextension -> <repo>/game/unmapped.gdextension
  viewer/              -> <repo>/game/viewer/
  ...                     one link per entry of game/
  bin/                    real folder: the extension's output directory
    libunmapped_gdext.so  (Windows: unmapped_gdext.dll)
  .godot/                 real folder: Godot's cache
```

- The library is built straight into `<build>/game/bin/`. `game/unmapped.gdextension` names it as `res://bin/libunmapped_gdext.so` (Linux) and `res://bin/unmapped_gdext.dll` (Windows), relative to the project, so the committed file is the same on every machine.
- After each build of the library, `gdext/cmake/assemble_project.cmake` makes one link per entry of `game/` (new files appear without reconfiguring; links to deleted entries are removed) and writes `.godot/extension_list.cfg`, so the viewer runs straight after a build.
- Links: symbolic links on Linux. On Windows, folders are directory junctions (no administrator rights or Developer Mode needed); files are symbolic links where Windows allows them, else hard links, else copies (with a warning). **Not yet tried on Windows.**
- Each build tree has its own run copy, so several presets and worktrees never share a library or a cache.
- The editor edits the repository's files through the links: scenes saved in `viewer/` land in `game/viewer/`.
- One caveat: when the editor saves a file at the project root (in practice `project.godot`, from Project Settings) with "safe save" on, it writes a temporary file and renames it over the link, so the run copy gets a real file and the repository copy is not updated. The next build notices that the file differs from the repository's and warns, without overwriting it; copy the change across by hand. Project settings are rarely changed and are best edited in `game/project.godot` directly.

Do not open `game/project.godot` itself in the editor: the extension is not there (no `bin/`), and the editor would create `game/.godot/` in the repository.

## Classes

All in `gdext/src/`, registered at the scene level:

| Class | Base | Role |
| --- | --- | --- |
| `WorldFile` | `RefCounted` | Data access: a `world.db` opened read-only through `worldgen::db::WorldReader`. `open(path)` returns false with `get_error_code()` (worldgen's code name: `file_unreadable`, `not_sqlite`, `not_world`, `unsupported_schema_version`, `meta_key_missing`, `meta_value_invalid`, `corrupt_layer`, ...) and `get_error_message()` (worldgen's plain-English message). `get_meta_entries()`, `get_meta_value(key)`, `get_layer_count()`, `get_layer_names()`, `get_layer_info(i)` (id, name, width, height, element_type, codec, encoded_size; no decoding), `read_layer(name)`. Table `biome` (schema 3) is read once on open through the reader's table access and worldgen's `read_biome_rows`: `get_biome_entries()` (id, key, name, colour, water) and `get_biome_table_problem()`; a world without the table opens normally. Table `region` (schema 5) likewise, checked by worldgen's `read_region_rows`, with the name taken from column `name`: `get_region_entries()` (id, name, biome, cells), `get_region_name(id)` and `get_region_table_problem()`. `get_composite_names()`: the composites worldgen can build from the file (`map` with an `elevation` layer, `biomes` with `biome` and a usable table too, `regions` with a `region` layer as well). |
| `WorldLayer` | `RefCounted` | A decoded layer: integer cells, `get_cell_text(x, y)` (exact decimal, also for u64), `get_min_text()`, `get_max_text()`, `get_palette()`, and `to_image()`, an RGB8 `Image` made by worldgen's `render_rgb` at scale 1 with worldgen's `auto_palette` for the layer (as `worldgen-cli render --palette auto`) and, for the `biome` palette, the world's table `biome` (P1-00 10.2: without it every cell is magenta), rendered straight into the image's buffer; the same pixels as `worldgen-cli render`. `composite_image()` (C++ only) does the same for worldgen's composites (`render_composite_map`, `render_composite_biomes`, `render_composite_regions`). |
| `ViewerModel` | `RefCounted` | The model of the viewer screen: the open world, its views (every layer, then every composite), the selected view, decoded layers and images; `get_view_count()`, `get_view_info(i)` (kind `layer` or `composite`, name, group, unit, size, element type, palette), `select_view(i)`, `get_view_image(i)`; `get_legend()` and `get_legend_title()` for the selected view; `describe_cell(x, y)`, one line with the cell, its value in display units, its biome and region names and, with history, who holds the region in the current year; signals `world_opened`, `world_open_failed`, `world_closed`, `view_selected`, `view_failed`, `year_changed`, `view_image_changed`, `markers_changed`. The history methods of spec P4-03 3.2 and the marker methods of spec P4-04 8.1 (below). No Controls; a VR view can use it as is. |
| `LayerMapView` | `Control` | Presentation: draws one layer image with nearest filtering, pan (drag with left or middle button), zoom about the cursor (wheel), fit (double click); signal `cell_hovered(x, y)`. Given the same `Image` again (redrawn in place) it updates its texture and keeps pan and zoom. Draws the markers above the image (`set_markers(markers, glyphs)`, P4-04 8.4) and hit-tests them under the mouse (signal `marker_hovered(index)`, -1 for none; `get_marker_screen_position(index)`). |
| `YearMarks` | `Control` | Presentation: the marks under the year slider (P4-03 4.5), one line per awakening, phase start and the present; its tooltip names the nearest mark. |
| `ViewerScreen` | `Control` | The flat view: root of `game/viewer/viewer.tscn`; finds its parts by unique name, wires them to a `ViewerModel`, reads the command line, runs the headless check and `--bench`. The layer list shows every view under group headings, Composites first (Terrain, Water, Climate, Biomes, Resources, Regions, Other follow); a world opens on the first entry. The legend panel shows the selected view's colours; the line under the map describes the cell under the mouse; the year bar under the map sets the year. |

`HistoryState` (`gdext/src/viewer/history_state.hpp`, C++ only, not registered) is what the model holds of the history: worldgen's `LoadedHistory` (`load_history`, read once when a world opens), the civilization colours (`civilization_colours`), the current year Y with its `YearState`, the holder vector and fill of the territory image (`territory_holders`, `territory_fill`), the `TerritoryBase` once built, and the holder vector the image was last drawn with, which alone decides whether a year change redraws the image. It holds no Godot types.

### Markers in the viewer (spec P4-04 Part B)

- **Model.** `HistoryState` builds worldgen's `MarkerIndex` once, after `load_history`; a failure leaves the history loaded and the markers unavailable, and the file label gains `markers: <code>: <message>`. It holds the options (faded ruins off, event places on, passes on), the enabled flag (on) and the current `YearMarkers`. On a year change (after the territory image, before the legend), an option change or the flag, it computes `markers_at` into a scratch set and swaps it in only when the settlements, places or passes differ (the year alone is no difference); only then does the model emit `markers_changed`. Bound: `get_markers_available()`, `get_markers_enabled()` / `set_markers_enabled(on)`, `get_marker_option(name)` / `set_marker_option(name, on)` (`faded`, `events`, `passes`), `get_markers()` (in the draw order of 6.1: `{type, id, x, y, glyph, fill, capital, small, events}`), `get_marker_glyph(name)` (`{radius, cells}` from worldgen's `marker_glyph`), `describe_marker(index)` (the hover texts of 8.5; sentences by worldgen's `render_event`) and `get_marker_legend()`.
- **Screen.** The sidebar's Markers group (between the views and the meta panel): `%MarkersToggle` "Show markers" (key **M**), `%MarkFaded`, `%MarkEvents`, `%MarkPasses` and the key list `%MarkerLegend`, all disabled without markers. On `markers_changed` and `view_selected` the screen hands `get_markers()` and their glyphs to the map view, so markers show over every view; no marker is drawn into a view's image.
- **Drawing.** Glyphs are drawn at screen size: each glyph cell is g x g screen pixels, g = 1 below zoom 4 (screen pixels per cell), 2 below 10, else 3, centred on floor(offset + (x + 0.5) zoom); below zoom 0.5 hamlets, villages that are not capitals, ruins and faded ruins are left out. Each distinct (glyph, fill, g) is one cached `ImageTexture` (dropped when the world closes), so a frame is one `draw_texture` per marker. Hover tests the glyph cells in reverse draw order (any class but none: a declining settlement's interior counts, the inside of a ring does not, so a settlement in a ring is hit); while a marker is hit, the line under the map shows its description instead of the cell's.

### History in the viewer (spec P4-03)

- **Reading.** `ViewerModel::open_world` calls worldgen's `load_history` on the open file (`WorldFile::reader()`, C++ only; the extension issues no SQL). The history status is `none` (a world without history, `history_missing`, or no world open), `loaded` (Y = E, the present) or `failed` (any other error, with worldgen's code and message: the world still opens with its geography, the file label gains a line `history: <code>: <message>`, the year bar is disabled).
- **Methods** (bound): `get_history_status()`, `has_history()`, `get_history_error_code()`, `get_history_error_message()`, `get_end_year()`, `get_year()` (-1 without history), `set_year(y)`, `step_year(delta)`, `step_event(direction)`, `step_holder_change(direction)`, `has_previous_event()`, `has_next_event()`, `has_previous_change()`, `has_next_change()`, `get_year_info()`, `get_year_marks()`, `get_region_holding(region)`, `get_civilization_info(civ)`, `get_civilizations_alive()`, `get_territory_view()`. None throws into Godot.
- **The territory view.** With history and the composite `regions` available, the first composite is `territory`, so the world opens on it: worldgen's `render_territory` at Y (the same bytes as `worldgen-cli render --composite territory --year Y`). Its base is built on first display; a year change whose holders differ from the image's redraws it in place into the same `Image` (`view_image_changed`), so quiet years cost nothing. Its legend: the realms alive at Y under their race's plural, the two border rows and the free-land rows of `regions`.
- **The year bar** (`YearBar` in the scene): -25, -1, previous event, previous change of holder, the slider over the year marks, next change, next event, +1, +25 and a year field; under it the year readout and the counts of the year. Keys, when no text field has focus (`_unhandled_key_input`): Left / Right one year, Shift with them 25, Page Up / Page Down the previous / next event, `[` / `]` the previous / next change of holder, Home year 0, End the present. The year buttons, the slider and the map view take no keyboard focus (`focus_mode` none in the scene), so the arrow keys reach the year bar instead of moving focus; the layer list and the meta panel still take focus when clicked, and while one of them has it the arrow keys act on it.
- **Hover.** With history, the cell description of every view ends with `   |   held by <realm> since <Y>`, `   |   free since <Y>` or `   |   free` for the cell's region at Y.

Command line additions (after `--` with a world path): `--year <Y>` opens at year Y; `--faded` starts with the faded ruins shown; `--bench` times opening the world and a year change to every year 0 to E and back, prints the figures (`UNMAPPED-BENCH:` lines: open, first territory image, mean and slowest year change, number of image redraws and the slowest, the mean and slowest marker step and the number of `markers_changed`, then, on the next frame, the time of one marker draw; headless there is no frame, and the line says so), and quits; it runs headless, or under `xvfb-run` for the draw time:

```
"$GODOT" --headless --path "$B/game" -- ~/.cache/the-unmapped/out/seed42-1024.db --bench
```

The viewer takes what it knows of the layer catalogue of spec P1-00 section 4 from worldgen's `worldgen/inspect/layer_catalogue.hpp` (spec P4-02; plain C++, model side): each layer's group, its unit, the display form of a value (`123.4 m`, `12.3 °C`, `lake`, `142 / 255`, `48 m offshore`, ...), the legend of each palette and composite and the composite's description, the composites a world can show (`available_composites`) and region names (`region_name` over the `RegionRecord`s of `read_region_rows`, which carry the name and biome). The extension keeps no copy of any of it and reads no column of table `region` itself. Legend colours are computed with worldgen's own palette functions and ramp stops, so each swatch is the colour drawn; the biome rows come from the world's table `biome`. A layer the catalogue does not list goes under Other and shows its raw value; its legend is worldgen's palette for it (for gray: the minimum and maximum).

Integers stay integers up to `WorldLayer`; floats appear only on the Godot side (zoom, pan) and never reach worldgen. The viewer lists whatever layers the file holds, so new layers appear without viewer changes; each is drawn with worldgen's palette for it (a new palette needs no viewer change either, unless, like `biome`, it needs data from a table). Composites appear when worldgen offers them for the file's layers.

## Opening the viewer

After building with the option on (Linux, `linux-gcc-debug` tree; substitute your preset):

```
B=~/.cache/the-unmapped/build/$(basename "$PWD")/linux-gcc-debug
GODOT=~/.cache/the-unmapped/tools/godot-4.7.2-stable/Godot_v4.7.2-stable_linux.x86_64
"$B/tools/worldgen-cli/worldgen-cli" generate --seed 42 --test-pattern --out ~/.cache/the-unmapped/out/seed42.db
"$GODOT" --path "$B/game" -- ~/.cache/the-unmapped/out/seed42.db
```

Add `--view <name>` after the path to start on that layer or composite (for example `--view regions`), and `--hover <x> <y>` to show that cell's description as if the mouse were over it (the cell only, never a marker). For screenshots, `--zoom <z> --centre <x> <y>` shows cell (x, y) in the middle at z screen pixels per cell, and `--mouse <x> <y>` sends a mouse motion over that cell's centre, so a marker there is described (P4-04). `--screenshot <file.png>` saves the window after one second and quits (needs a display; on a desktop without one, `xvfb-run -a -s "-screen 0 1600x1000x24"` in front works). A real world: `worldgen-cli generate --seed 42 --map-size 512 --out <file>` (about 2 seconds). Without a path after `--`, use "Open world..." to pick a file. The path must be absolute: Godot changes the working directory to the project. To edit the scenes in the editor: `"$GODOT" --editor --path "$B/game"`.

## Headless check

CTest test `gdext-headless-check`, registered when the option is on, tests are built and the pinned editor is found. It runs `gdext/cmake/headless_check.cmake`:

1. `worldgen-cli generate --seed 42 --test-pattern` into `<build>/gdext/headless-check/pattern/`, and `worldgen-cli render` of each of its three layers to PNG.
2. `worldgen-cli generate --seed 42 --map-size 512 --data <repo>/game/data` into `<build>/gdext/headless-check/real/`; its layers are listed from `worldgen-cli report` (`[layers]`), `biome`, `elevation`, `rainfall` and `region` must be among them, and every layer is rendered to `<layer>.png` and the composites `map`, `biomes` and `regions` to `composite.<name>.png`. Then (P4-03 10.1) `report --history --level full` into `history.txt`, from which the script takes E, the age start years and the year F of the first `region_ceded` event; the world must have a ceded region, a war, a ruined settlement and an ended civilization (otherwise the check fails and asks for another seed, to be recorded here: seed 42 at 512 has them at generator 0.21.0); the territory image is rendered at E (`composite.territory.png`) and at each year of L = {0, every age start, F - 1, F, floor(E / 2), E - 1, E} (`territory-<Y>.png`).
2b. The same seed and size with `--until regions` (a world without history) into `geo/`, rendered as step 2.
3. `godot --headless --path <build>/game --import`: the editor loads the project and the extension.
4. For each world, `godot --headless --path <build>/game -- <world> --check <dir> --expect-layers <n> --expect-composites <m> --expect-history <none|loaded>` (the real world also `--expect-end-year`, `--expect-years` and `--history-report`): the real viewer scene opens the world, the check (`gdext/src/viewer/viewer_check.hpp`) chooses each layer and composite through the layer list and compares the image handed to the map view with the PNG, pixel for pixel; it also checks the meta panel, that table `biome` was read and no `biome` cell is drawn in the unknown-biome magenta, and two reader errors. For the screen it checks that the list shows every view once under non-selectable group headings, the composites first, and that the world opens on the first entry; that every view has a legend (title and rows, the list showing every row), that the legend of the `biome` layer lists every row of table `biome` by name and colour and that of `biomes` and `regions` every land row, and that `regions` has the black border row; that hovering a cell of a region describes it with its coordinates, elevation in metres, biome name (table `biome`) and region id and name (table `region`), and that leaving the map restores the prompt; and the display form of a few units. Without history (pattern and geography-only worlds) it checks that there is no `territory` view, the year bar is disabled, the year cannot be set by method or key, and the hover text names no holding (P4-03 N1 to N3). With history (P4-03 H1 to H8): the world opens at E on `territory`, listed first; for each year of L, set through the slider, the map view's pixels equal `territory-<Y>.png`, the year readout matches the ages and phases of `history.txt` and the legend lists exactly the realms alive then by race; at E every realm of `[present]` holds its number of regions and the rest are free; the steps by event, by change of holder (against a year-by-year search through the model) and by 25 years, each emitting `year_changed` once; the keys; the hover text of a held and a free region at E and at 0; every civilization's colour and legend swatch against worldgen's `civilization_colours`; and the year marks. It prints the open time, the first territory image's time and the slowest year change as information. Markers (P4-04 9; the script also takes from `history.txt` R0, the smallest `ruined <year>` of the `[present]` settlement lines, and D0, the year of the first `ruin_faded` event, and from `report --db` the number of passes, and renders `worldgen-cli render --composite territory --year Y --markers` for each year of LM = {0, D0 - 1, D0, R0 - 1, R0, F, floor(E / 2), E} into `markers-<Y>.png`, with `--faded` at E and D0 into `markers-faded-<Y>.png`, and `render --layer elevation --year R0 --markers` into `elevation-markers-<R0>.png`; the viewer gets `--expect-marker-years` and `--expect-passes`): M0 without history no markers, every control disabled and key M doing nothing; M1 at open the markers on with the default options and the key list of 8.6; M2 the settlement entries at E against the `[present]` lines and the capitals against the `[civilizations]` blocks; M3 each ruin standing the year before and a ruin in its year, each `ruin_faded` settlement a ruin the year before and then absent or faded; M4 the places' events against the chronicle's placed events for the years of LM and the first 20 years with a placed event, at the settlement's or the region seed's cell; M5 the passes; M6 for each year of LM the territory view's image with the model's markers drawn by worldgen's `draw_markers` against `markers-<Y>.png`, likewise with faded ruins and the elevation view, and `get_markers()` in the order of 6.1; M7 the hover texts of a standing settlement, a capital and a ruin, a mouse motion over each, over the centre of a ring around a settlement and away from every marker; M8 the toggles and key M with one `markers_changed` per change and none when nothing differs; M9 `markers_changed` over 0 to E in exactly the years whose marker set (from the check's own `MarkerIndex`) differs from the year before.

It fails unless every step exits 0 and the viewer prints `UNMAPPED-CHECK: PASS` for both worlds. It takes about 7 seconds (`linux-gcc-release`), most of it generating the 512 world. Run it alone with `ctest --preset <preset> -R gdext-headless-check -V`.
